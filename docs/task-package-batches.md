# Project-local fixed task package batches

`POST /api/projects/{project_id}/task-packages/batches/` requires the existing fixed-package feature, a currently authorized project manager, an allowed project lifecycle state, PostgreSQL, and a UUID `Idempotency-Key` header. It accepts `name`, optional `instructions` and `source_note`, explicit `task_ids`, and `batch_size`. Task IDs must be distinct and belong to the project; the request is limited to 1–1,000 tasks and at most 100 packages, each containing at most 1,000 tasks. IDs are sorted ascending (rule `task-id-ascending-v1`) and consecutive chunks form packages. A short final chunk is retained. Each package name has an ordinal suffix (the supplied prefix is truncated if needed); instructions and source note are copied; this creates no assignments or claims.

All packages, their items, and the receipt commit in one project-fenced transaction. The response contains the batch ID and package IDs with the original member IDs. Retrying the identical normalized request with the same key, authenticated principal, and current authorization returns the original receipt with `replayed: true`; a different request or principal using the key conflicts. A client which did not receive a response should preserve and retry the original key and body, never assume timeout means rollback. Revocation, lifecycle restrictions, unavailable receipts, and deletion do not prove that the transaction did not commit. The receipt is project-local and is deleted when the project is deleted; it is not a durable cross-system audit log or a task content snapshot. Task items retain original IDs if individual tasks are deleted.

The batch receipt is separate from the existing single-package key namespace. No host integration, external source mapping, distributed transaction, or pre-commit visibility protection for previously existing tasks is provided. Project and shared database locks can affect concurrent operations. Reversing the batch migration is intentionally blocked while receipts exist.

## Existing asynchronous import provenance

An optional `project_import_id` binds the request to an existing `ProjectImport` in the same project. Creation locks and verifies that the import completed with `commit_to_project` and `return_task_ids` enabled, that its recorded task IDs are valid, unique, number at most 10,000, and match the recorded count, and that every selected task is in that list. The selected task creation timestamps must fall between the import record creation and its recorded completion. The receipt snapshots the import ID, the creation and completion timestamps, task count and a hash of its sorted task IDs; package items also retain each selected task's original ID and creation time. The import ID is part of the request fingerprint. A replay returns the committed snapshot even if the import record was subsequently removed, while a new request cannot use an unavailable or unverifiable import. The full import task list is not copied into the receipt: its hash cannot reconstruct the list or independently prove subset membership after the original list is lost.

This is evidence derived from the existing import record, not the immutable `ImportBatch` ledger contemplated by #87. Existing imports without persisted task IDs, synchronous imports with no `ProjectImport`, and file-upload IDs alone cannot establish this association and are rejected when an import ID is requested. `finished_at` is populated on completion by the updated import worker; older records without it are rejected. It is not a cryptographically immutable completion timestamp; privileged database edits or ID reuse within that time window cannot be ruled out by this historical record. It does not establish original file bytes, a content hash, an external identity, or immutable task content. A later reimport does not transfer provenance to replacement tasks. No source is asserted when the optional import ID is absent; `source_note` is user-supplied text.

For example, provide a completed import ID and an explicit subset of its recorded tasks:

```json
{"name":"Review set","task_ids":[101,102,103],"batch_size":2,"project_import_id":42}
```

The task IDs and import ID above are illustrative, not existing records. Clients must keep the original request and UUID key for recovery; a missing receipt or an access denial is not evidence of rollback.

To bound project-lock work and application memory, import records with more than 10,000 task IDs are rejected before their task ID JSON is fetched by the application. This does not bound the database storage occupied by existing imports. A larger source requires a separately designed bounded provenance ledger.
